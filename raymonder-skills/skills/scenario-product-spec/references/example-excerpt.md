# 金标准范例（照着模仿语气与颗粒度）

下面是一段**通用示意**（活动报名系统的"取消与退款"，与任何具体招标项目无关），示范了：① 角色+场景+条件+响应的句式；② 分流规则写成"若 A…若 B…"；③ 每条回标需求编号（这里用占位编号 `REQ-##`，**实际写作时换成目标项目招标/需求文档里的真实编号**）；④ 末尾配"端到端链路"文字 + 指向流程图；⑤ 详略得当、读起来像业务剧本。**对标这个颗粒度，编码体系按你的项目实际替换。**

---

## 示例：取消与退款（按原付款方式分流）

退款是报名模块业务规则最严的一段，产品逻辑是"**按原付款方式严格分流 + 按比例计算 + 负责人审批 + 回写账务**"：

- 职员可从活动视角取消单笔或多笔报名（REQ-01）；取消成功后，已被这笔报名占用的名额随即释放（REQ-02）；但**已取消报名的历史出席记录会被完整保留**，同时系统不允许再对未消耗的场次补记出席（REQ-03）。
- **免费活动无需退款**；对付费活动，系统则依据**原始付款方式**走严格的退款逻辑（REQ-04）。
- **按比例退款**（REQ-05）：系统参考剩余与已选场次及出席记录自动算出按比例的退款额（例如 10 个场次里有 7 个未使用，则退 7/10），同时保留职员手动改额的灵活性；被退款的场次，其出席记录会被相应标记。
- **分流规则**是这段的核心，按付款方式走两条完全不同的路径：
  - 若原付款是**信用卡**，系统**必须原路退回当初那张信用卡**，不允许改退到别处（REQ-06）；
  - 若原付款是**非信用卡**（转账 / 即时支付 / 支票 / 现金），系统会触发一个**安全的、免登录的一次性链接**，让参与者自己选择偏好的退款方式并填账户信息，链接在成功提交后即失效（REQ-07）；职员也可代参与者勾选替代退款方式（REQ-08）。
- 管理员可**自行新增和管理退款方式**（REQ-09）；**捐款一律不退**（REQ-10）。
- **所有带退款请求的付费取消，都必须经负责人审批工作流**才能执行（REQ-11），各节点经邮件/站内通知告知用户与同事（REQ-12），退款数据经 API 回写账务系统（REQ-13），并配退款记录列表供查阅（REQ-14）。

> **端到端链路**（取消退款）：发起取消 → 判断免费/付费 → 免费则直接释放名额；付费则按原付款方式分流（信用卡原路退 / 非卡走一次性链接选方式）→ 负责人审批 → 回写账务 → 通知会员 → 名额释放并触发候补转正。配一张决策分支流程图（feishu-editable-diagrams）。

## 为什么这段是"好"的

1. **每条都有主体和场景**："职员可从活动视角取消"、"系统会触发一个一次性链接"——不是裸的功能名。
2. **隐含业务规则被显性化**：信用卡 vs 非信用卡的两条路径、按比例退款的算法、捐款不退、必须审批——这些都是评审判断"你是否真懂退款"的关键。
3. **分流写成清晰的 if/else**，而不是"支持多种退款方式"一句带过。
4. **回标编号**贯穿，且不重复矩阵的逐条合规判定（编号用项目真实编码体系）。
5. **末尾给端到端链路 + 指明配图**，把碎片串成一条可视的业务流。
6. **详略**：退款是核心复杂点，所以展开成半页；而像"配退款记录列表"这种简单项就一句带过，不强行注水。
