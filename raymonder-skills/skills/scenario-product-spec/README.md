# scenario-product-spec

版本：0.9

场景化产品方案写作 skill，用于把功能清单、需求矩阵或 RFP 条款扩写成“角色 + 场景 + 条件 + 系统响应 + 业务价值”的完整产品叙事。

## 能实现什么功能

- 把干巴巴的功能短句改写成有业务逻辑的场景化描述。
- 为投标技术方案、产品方案、需求理解文档、解决方案设计和 PRD 组织端到端叙事。
- 按模块讲清业务主线、角色权限、关键规则和复杂链路。
- 在段落中回标原始需求编号，方便和需求矩阵互相对应。
- 为复杂流程补流程图、状态机、时序图或效果图的制作建议。
- 帮助非技术评审理解“产品怎么用、业务怎么转、为什么这样设计”。

## 安装方式

把仓库 clone 到你的 agent skills 目录即可，例如 Codex：

```bash
cd ~/.codex/skills
git clone https://github.com/raymonder/scenario-product-spec.git
```

目录结构应保持为：

```text
~/.codex/skills/
└── scenario-product-spec/
    ├── SKILL.md
    └── references/
```

安装后重启 agent，或重新打开会话，让 skill metadata 被重新加载。

## 怎么使用

在对话中提出产品方案或需求改写任务即可，例如：

```text
把这份功能清单改写成场景化产品方案。
```

```text
这个 RFP 的需求太干了，帮我扩写成有业务叙事的技术方案。
```

```text
按模块写报名、支付、退款的场景化产品说明，每条回标需求编号。
```

最好同时提供：

- 原始需求清单、需求矩阵、RFP 条款或已有方案。
- 目标文档位置：本地 Markdown、Word、飞书 docx / wiki 等。
- 项目已锁定口径：技术架构、产品边界、术语、可选模块、报价或范围限制。
- 原始需求编号体系，例如 `REQ-001`、`FR-2.1`、`需求 3.2.1`。

## 写作公式

核心公式：

```text
谁在什么前置设置或业务场景下，
当满足什么条件时，
系统如何响应，
以及为什么这样设计。
```

示例：

```text
管理员可为每个场次设定开始时间；在该场次的安排日期与时间到来之前，系统一律阻止记录出席，避免提前误签。
```

这类写法比“场次开始前不可记出席”更能体现产品理解。

## 推荐输出结构

- 开篇说明：本文和需求矩阵的分工。
- 产品理解总览：业务主线、角色和权限模型。
- 逐模块叙事：产品逻辑、关键规则、复杂链路。
- 端到端链路提示：对最复杂流程单独说明。
- 附录：模块和需求编号速查表。

## 主要限制

- 不负责决定产品是否应该做某功能；它主要负责“怎么讲清楚”。产品边界和承诺范围仍需由项目负责人确认。
- 不能乱改已锁定口径。架构、术语、模块边界、技术选型必须和其他方案文件一致。
- 字段级、界面级细节在需求未冻结前应写成“以最终原型 / 后续确认为准”。
- 需要原始需求编号才能稳定回标；没有编号时只能先建立临时编号。
- 不适合直接复制需求矩阵；矩阵讲合规判定，本文讲业务场景和产品叙事。
- 流程图和效果图依赖额外工具，例如 `feishu-editable-diagrams`、`gpt-image-2` 或飞书相关 CLI；没有这些工具时只能先输出文字图稿或 Mermaid 草案。

## 维护建议

- 把常用句式和反例持续补充到 `references/writing-pattern.md`。
- 把高质量项目片段沉淀到 `references/example-excerpt.md`，作为下一次模仿的语气样本。
- 图表制作流程有变化时更新 `references/diagrams-and-visuals.md`。
- 保持 `SKILL.md` 聚焦核心工作流，长例子和工具细节放在 `references/`。
