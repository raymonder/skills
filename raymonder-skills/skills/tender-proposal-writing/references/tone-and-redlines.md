# 通用腔调与红线

写标书任何一章前先读这一篇。它管的是「用什么口吻写、什么绝对不能写」。

---

## 一、核心腔调：主动方案，不是招标回声

**目标感受**：评审读你的方案，应该觉得「这家供应商把我们的业务摸透了，主动给了一套自洽、想得很周到的方案」，而不是「这家把我们的需求逐条换了个说法抄回来了」。

招标回声的典型症状是：通篇「我们将满足……」「针对贵方要求的 X，我们提供 X」「按照需求 3.2，系统支持……」。每条都贴着招标文件的结构和措辞走，读起来是被动应答。

主动方案的写法是：以**业务流程 / 解决方案逻辑**为主线来组织，把对方分散在需求清单里、没有明说怎么串起来的环节，用连续叙述补成完整链路；功能不是「被要求所以提供」，而是「业务这样运转所以方案这样设计」。

**对照（通用例子）：**

- 招标回声：
  > 根据需求 5.4，系统将支持多种退款方式。
- 主动方案：
  > 退款依据情形区别处理，而非一刀统一：系统先判断订单是否免费，免费则直接释放资源；付费则按原始支付方式分流——原路退回或经一次性安全链接由用户自助选择，确保每一笔退款都锁定在原始交易上、可对账可追溯。

- 招标回声：
  > 我们将提供符合要求的权限管理功能。
- 主动方案：
  > 全体用户从同一入口登录，登录后能看到什么、能操作到哪一级，并非由单一角色决定，而是由所属组织、岗位角色与审批层级三者叠加判定——这套叠加规则贯穿全系统，后文各模块的可见范围与操作边界都建立在它之上。

## 二、去标腔的具体手法

把已有的、带招标腔的稿子改顺，常用这几招：

1. **先给业务画面，再讲功能 / 看图。** 每个模块、每张流程图前，先用一两句话把「这块业务在整体里处于什么位置、一个典型动作怎么发生」讲出来，让读者形成画面再进入细节。

2. **把要求补成链路。** 招标文件里 A、B、C 三个要求是分开列的，你要在叙述里把它们串成「A 发生后触发 B，B 完成后进入 C」的连续流程，体现你理解它们之间的业务关系。

3. **能力陈述化。** 表格里、小标题里的「产品价值 / 功能说明」一列，从名词短语改成「能做到什么」的能力陈述。例：`权限管理` → `同事以机构账号一次登录，系统按其组织与职级自动配权限、自动串联审批链`。

4. **状态机 / 分支讲清「规则」而非「按钮」。** 涉及生命周期、审批、分流的地方，讲清楚「在什么条件下从哪个状态转到哪个状态、谁能触发、为什么这样约束」，而不是罗列界面上有哪些操作。

## 三、措辞红线（什么不要写）

1. **不写教导口吻。** 删掉「打个比方」「比如说」「众所周知」「简单来说」这类像在给读者上课的词，改成直接陈述方案如何运作。评审是专业的，不需要被科普。

2. **不夹口语和不易翻译的比喻。** 「一刀切」「运营驾驶舱」「打通任督二脉」这类口语 / 比喻，换成正式书面表述。**特别是当方案后续要整体译成英文时**，这类表达会成为翻译障碍——提前用规范书面语写。

3. **正文不夹 emoji、不夹随手批注。** 正文保持干净、正式。审读发现的问题不要用括号注在正文里。

4. **不堆空洞形容词。** 「先进的」「领先的」「强大的」「世界一流的」单独出现没有信息量。要么删掉，要么换成可验证的具体能力或指标（「页面响应 ≤2 秒」「支持 1000 并发」）。

5. **不写无法回溯的承诺。** 每句承诺都要能指回某条招标要求或你的数字底座 / 锁定决策。凭空加码的功能、含糊的「等」「灵活支持各种」要么写实、要么删。

## 四、竞品与对比红线（重要）

**正文里不点名对比竞争对手，也不暴露你的内部参考来源。**

- 介绍经验时，只讲「我方在同类项目中做过什么」，**不要**写「某某友商怎么做、我们和某某的差异、相比某产品我们更好」。
- 如果你复用了某个**内部已有项目 / 客户案例**作为提速素材，正文里把能力写成「我方在同类项目的经验」，**不要**出现那个具体项目 / 客户的名字（除非该客户已授权在「参考项目」里具名披露，且与本次招标无利益冲突）。
- 复用旧素材时，凡是与本次锁定口径冲突的，**必须改写或删除**：架构口径、技术选型、托管方式、产品里没有的整块功能、报表 / 数据口径，都要换成本次方案的设定。复用一段就顺手扫一遍是否有「漏网」的旧口径或旧名字。

> 自检动作：交稿前全文搜一遍竞品名、内部项目名 / 客户名、旧技术口径关键词，确认正文（「公司经验 / 参考项目」章节经授权具名的除外）里一个都不剩。

---

## 五、口径固定（全文一致性）

把「锁定决策」清单里的每一项当成全文不可偏离的口径：

- **术语统一译法**：同一个概念全文一种叫法 / 一种译法。中英 / 繁简撞名的（例如两个不同状态被译成同一个中文词）必须强制区分。
- **技术 / 架构口径固定**：选型一旦锁定，全文统一；禁止出现与之冲突的替代说法（例如已定方案 A，正文别再冒出方案 B 的字眼）。
- **可选模块边界一致**：哪些是核心交付、哪些是可选 / 预留，全文表述一致，且与报价拆分对得上。
- **语言分层规范**（按项目实际设定并全文统一）：常见做法是正文用一种语言、界面文案示例用目标地区语言、配图文字统一用另一种语言——具体怎么分由项目定，但定了就全文照办。

改任何一处口径，都要回到锁定决策清单更新，再全文同步，避免「改了正文忘了改表格 / 配图」。
