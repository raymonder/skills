# 投标方案撰写方法论（Tender / RFP Proposal Writing）

## 这个 skill 解决什么问题

一份标书最容易写成「招标文件的回声」——逐条把对方的要求换个说法抄回去，每条一句话，读完知道「你打算做」，却感受不到「你真的懂这门业务、方案是你主动设计出来的」。同时多人分头写各章，常出现腔调不一、口径打架、报价 / 工期 / 人力三处数字对不上、同一个术语两种译法。本 skill 给出一套贯穿全标书的打法，让方案读起来像**「我方深入理解了招标方的业务后，主动给出的一套自洽方案」**，并且全文口径一致、数字可对账、每条承诺都能回溯到招标要求。

核心理念一句话：**先把事实和决策固化成可回溯的底座，再用「主动方案」的腔调把它讲透，全程靠统一口径和单点对账防矛盾，把逐条追溯和审读说明剥离出正文。**

## 适用与不适用

适用：政府 / 企业 / NGO 的招投标响应文件，RFP / RFQ / ITT 响应，技术建议书 / 商务标 / 产品方案 / 报价书，以及对已有标书的改写、去标腔、查口径。

不适用 / 边界：本 skill **不替用户拍板**技术选型、架构口径、报价数字、团队名单——这些是「讲什么」，由用户或方案负责人决定；本 skill 只管「怎么讲、怎么组织、怎么对齐」。遇到这些待定项，应提示用户确认，并按「待确认项」挂起（见下文）。

## 一、开工前先建「事实底座」（最重要的一步）

不要拿到招标文件就开始写正文。先花时间把底座搭好，后面所有章节都站在它上面：

1. **吃透招标文件，逐条编号化。** 把招标正文 + 各附录（需求清单、工作流、评分办法、合同条款）通读，必要时逐字翻译 / 校对，确保不漏不误。把功能 / 技术需求**整理成带编号的清单**（沿用招标文件原始编号体系，如 `REQ-001`、`FR-3.2.1`、附录表行号等）。记录：需求总条数、评分项与权重、提交截止时间与方式、硬性格式要求（文件命名、份数、章节顺序）。

2. **抽出「锁定决策」清单。** 凡是用户已拍板、必须全文统一的事项，集中记一处：架构 / 技术选型口径、可选模块边界、关键术语的统一译法、命名规范、报价总盘与口径。一旦锁定，全文不得偏离（见 `references/tone-and-redlines.md` 的「口径固定」）。

3. **建「数字底座」。** 把容易前后矛盾的少数关键变量集中托管在一张表里：**报价金额 ↔ 人日 / 工期 ↔ 团队人力 ↔ 甘特图**必须互相对得上。任何一处要改，回这张表改，再同步出去。

4. **（推荐）写一份「交接简报 / 上下文文档」。** 把上面三项 + 文档结构 + 链接 + 写作规范 + 待办，整理成一份「自带上下文、可当首条 prompt」的文档。换 session、换人、换 AI 接手时整篇喂进去即可，不必重读全部原始材料。决策有更新就升级版本（v1 = 开工前事实底座，v2 = 已拍板决策……），始终以最新版为准。

> 为什么先做这步：标书的核心竞争力是「证明你真懂对方业务」，而这建立在你比对方更清楚地掌握自己的事实和决策之上。底座没搭好就写正文，必然出现承诺无法回溯、各章互相打架。

## 二、贯穿全文的通用规矩

这几条对**每一个章节**都生效，是本 skill 的总纲。详细展开和大量通用例子见各分册。

1. **腔调：写「我方主动给的方案」，不是「对招标文件的逐条回应」。** 读起来要像你理解了对方整套业务后主动把流程讲顺、把方案讲清，而不是对着需求一条条「我们满足 / 我们将提供」。详见 `references/tone-and-redlines.md`。

2. **场景化，不要功能清单。** 把干巴巴的一句要求，展开成「谁，在什么场景下，满足什么条件，系统 / 方案如何响应，为何这样设计」。产品 / 技术章节尤其要做到。详见 `references/sections-by-part.md` 与（若已安装）`scenario-product-spec` skill。

3. **逐条对比需求、但追溯剥离出正文。** 每条招标要求都要被响应到，用统一的合规分级（满足 / 部分满足 / 替代方案 / 不满足）逐条判定；但这套逐条追溯放进**专门的合规对照矩阵 / 附录速查表**，正文专注讲业务逻辑，不被编号淹没。详见 `references/requirement-traceability.md`。

4. **口径与数字全文一致。** 术语统一译法、技术口径固定、可选模块边界一致；报价 / 工期 / 人力三处数字对齐数字底座。改一处必须同步全文。

5. **承诺可回溯、不写死未冻结的范围。** 任何新承诺都要能指回某条招标要求或数字底座。细到具体字段 / 界面、依赖对方后续提供规格的部分，用「以最终原型 / 客户后续提供的规格确认为准」兜底，避免中标后做亏。

6. **审读发现的缺口不夹在正文里。** 通读时发现的「讲不清 / 前后不一致 / 待与对方确认」，统一列到文末「审读说明 / 待确认项」表，正文保持干净叙述、不夹批注。

7. **配图分类选工具、别过度配图。** 流程 / 状态 / 时序 / 分支类→可编辑流程图；总览 / 效果 / 概念类→精致位图。一个章节通常 0–1 张图，只在文字说不清的复杂链路才配。详见 `references/sections-by-part.md` 第「配图」节。

## 三、一份标书的通用文档地图

不同招标对章节的硬性命名和顺序有要求（**以招标文件规定的文件名与结构为准，不要自作主张改名**），但内容板块大体如下。每块的具体写作要求见 `references/sections-by-part.md`。

| 板块 | 回答评审的问题 | 常见评分维度 |
|---|---|---|
| 0. 主文档 / 总纲 | 这份标书怎么读、各部分在哪、怎么对应招标要求 | —（导航） |
| 1. 技术方案 | 你打算用什么架构 / 技术 / 工程方法把它做出来、做稳 | 技术满足度 |
| 2. 产品 / 解决方案 | 你是否真懂业务、方案在真实场景里怎么运转 | 业务理解、产品 |
| 3. 商务方案 | 排期、团队、方法论、SLA、资质、风险怎么安排 | 实施排期、资源、资质 |
| 4. 关于我们 / 为什么选我们 | 你是谁、做过什么类似的、凭什么是你 | 相关经验、增值 |
| 5. 财务 / 报价 | 多少钱、怎么拆、怎么付、含什么不含什么 | 价格（常占大头） |
| 6. 需求合规对照矩阵 | 每条要求你是否满足、怎么满足 | 技术满足度（兜底） |

> 评分权重决定详略：价格常占最大权重，但价格分往往靠「报价策略 + 拆价口径」拿，而**技术 / 产品 / 经验分**是你能靠写作质量真正拉开差距的地方，值得多投入。开工时先看评分办法，按权重分配精力。

## 四、工作流程

1. **建底座**（第一节）：吃透招标文件、编号化需求、抽锁定决策、建数字底座、写交接简报。期间**不要**先去翻文档格式 skill（docx/pptx 等），先把事实弄对。
2. **定结构**：按招标规定的章节名和顺序列出文档骨架；主文档做导航，各章拆成可独立推进的子文档。
3. **逐章写正文**（第二节规矩 + `references/sections-by-part.md`）：一次只写 / 改一块，先本地成形为 md 便于低成本迭代。条数最多 / 最复杂的模块重点展开，其余讲清逻辑即可，详略有别。
4. **建合规矩阵**（`references/requirement-traceability.md`）：逐条响应 + 分级 + 回标编号，与正文互补不重复。
5. **配图**：只在关键链路补，按内容性质选工具。
6. **查口径、对数字**：术语 / 口径全文一致；报价 ↔ 工期 ↔ 人力回数字底座对账；竞品红线全文扫一遍（`references/tone-and-redlines.md`）。
7. **收尾**：文末列「待确认项」；版本命名带 vN、旧版归档；更新索引 / 交接简报。只在用户要求的最终格式（docx/pptx/飞书等）阶段才去读对应的格式 skill。
