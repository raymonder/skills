# 各分章写作要求

一份标书每一块的目标读者、评分维度、写法都不同。这一篇按板块给出各自的要求、结构和通用例子。所有板块都先服从 `tone-and-redlines.md` 的通用腔调与红线、`requirement-traceability.md` 的回标方法。

> 章节的硬性命名和顺序**以招标文件规定为准**，不要因为觉得某个名字不好听就改名——招标方常按规定的文件名核对完整性。

---

## 1. 技术方案

**评审在问**：你打算用什么架构、技术栈、工程方法，把这套系统做出来、做稳、做得可扩展可维护？

**结构（典型）**：
1. 对项目的理解与方案总览（先证明你懂这要解决什么问题）
2. 总体架构（架构风格 + 为什么选它，尤其要呼应招标文件的偏好）
3. 核心业务流程的端到端理解（用流程图 + 文字旁白讲清主线）
4. 模块设计 / 隔离 / 高可用
5. 技术栈选型（一览表 + 选型理由）
6. 数据库与数据迁移
7. 环境、部署与托管
8. 安全与数据保护
9. 接口设计与系统集成（与外部系统的对接点、数据方向、集成方式）
10. 性能测试与优化
11. 非功能需求达成对照

**写作要点**：
- **架构口径全文锁死、且呼应招标偏好。** 招标文件若明示偏好某种架构 / 部署 / 合规要求（如数据须本地驻留），就顺着它来并讲清你如何满足；选型一旦定，全文统一，禁止冒出冲突的替代说法。
- **选型要给「为什么」，不只是「是什么」。** 每个关键选型补一句业务 / 工程理由，体现是权衡后的决定。
  - 反例：`数据库采用关系型数据库。`
  - 正例：`核心交易数据采用关系型数据库（主从架构），因报名 / 支付链路要求强一致与事务保证；分析类查询走只读副本，与生产写入物理隔离，避免高峰期相互争用。`
- **集成章节是技术分高地。** 把与每个外部系统的对接点、数据方向、集成方式（如 REST / Webhook / 幂等 / 限流 / 熔断）讲全，每个对接点尽量回标招标文件里的流程节点编号。
- **非功能指标写成可验证的数字**（并发数、响应时间、可用性 %、RTO/RPO、备份策略），不要只说「高性能、高可用」。

## 2. 产品 / 解决方案

**评审在问**：你是不是真懂这门业务？方案在真实场景里到底怎么运转？

这是体现「业务理解分」的主战场，也是最容易写成需求清单的地方。**核心动作：把每条功能从「功能短句」改写成「场景化业务语句」。**

> 若已安装 `scenario-product-spec` skill，这一块直接用它，本节是其精要版。

**黄金公式**：
> **谁（角色）** 在 **什么前置场景** 下，当 **满足什么条件** 时，**系统如何响应**（必要时补一句**为何这样设计 / 业务价值**）。

**对照（通用例子）**：
- 反例（功能短句）：`活动开始前不可签到。`
- 正例（场景化）：`管理员可为每个场次设定开始时间；在该时间到来之前，系统一律阻止记录签到，避免现场提前误操作。`

- 反例：`支持名额预留。`
- 正例：`面向「先占位、后付款」的场景，职员可为一批指定用户预先锁定名额；预留一经确认即扣减库存，但若在可配置时限内未转为正式订单，系统自动释放，避免资源被长期空占。`

**结构**：先「产品理解总览」画出端到端业务主线（那条骨架，如 A→B→C→D→E）和角色 / 权限模型，再逐模块叙事，最复杂的模块（条数最多、规则最密的）重点展开，其余讲清逻辑即可。附录给「模块 ↔ 需求编号速查表」回标。

**自检**：写完一段，把「系统 / 用户 / 当……时」这些词去掉后还成立吗？如果只剩一个名词短语，那还是需求清单，要再展开。

## 3. 商务方案

**评审在问**：你怎么组织实施？排期靠谱吗？团队够不够？出了问题怎么办？

**常见内容板块**：实施排期（甘特图）、团队组成与分工、实施方法论（如迭代 / 里程碑）、SLA 与运维支持、资质证明、合规承诺（如数据保护、安全审计配合）、风险识别与应对、保修 / 维护范围。

**写作要点**：
- **排期 ↔ 报价 ↔ 团队三处数字必须对齐数字底座。** 甘特图工期、报价人日、团队 FTE 三者要算得过来，这是评审常抓的矛盾点。
- **团队表写实。** 角色、人数、年限、相关经验如实列；真实姓名 / CV 若待补，明确标「待补」而非编造。
- **SLA 分级量化。** 按严重等级（P1–P4）给响应时间和解决目标，配可用性、灾备 RTO/RPO、备份策略。
  - 例：`P1（系统不可用 / 核心流程中断）：≤1h 响应、≤4h 解决；可用性承诺 99.5%；灾备 RTO ≤8h、RPO ≤3h。`
- **风险写成「识别 + 应对」成对出现**，只列风险不给对策等于没写。
- **方法论落到这个项目**，别堆通用术语；讲清在本项目里每个阶段产出什么、怎么和甲方协作验收。

## 4. 关于我们 / 为什么选我们

**评审在问**：你是谁、做过什么类似的事、凭什么把这单给你？

**结构（推荐「开门见山」）**：先用几条最有力的理由开篇（为什么是我们），再公司简介、行业专长、代表项目、资质认证。

**写作要点**：
- **开篇直接给理由，不要从公司沿革讲起。** 把最能打动这个评审的 3–5 点放最前面。
- **代表项目挑「同类」的。** 与本次招标业务类型最接近的项目优先；每个项目讲清规模、你解决了什么、可量化的成果（在客户授权披露的前提下）。
- **资质对口列。** 与招标要求 / 评分项对得上的资质、认证、软著、行业奖项优先；如果招标方本身已经是你的客户，务必写进来。
- **遵守竞品红线**（见 `tone-and-redlines.md` 第四节）：只讲「我方做过什么」，不点名对比友商；复用内部案例时不暴露未授权的客户名 / 项目名。
- 量化数字若涉及客户敏感信息，先确认是否可对外披露，不确定就写定性表述或标「待客户授权」。

## 5. 财务 / 报价

**评审在问**：多少钱、怎么拆的、怎么付、含什么不含什么？（价格常占最大评分权重。）

> 本 skill 不替你定价。定价逻辑、费率、总盘由用户 / 方案负责人拍板；本节只管「报价怎么组织和呈现」。

**写作要点**：
- **报价结构清晰、口径与正文一致。** 按招标要求的计价方式拆分（如按阶段 / 按模块 / 一次性授权 + 定制开发）；可选模块单独列、可加可减，且与产品 / 技术章节标的「可选边界」完全对应。
- **去掉铺垫和花哨描述。** 报价部分要干脆——结构 + 数字 + 条款，不要长篇「报价原则」铺陈。
- **数字底座单点对账。** 报价金额 ↔ 人日 ↔ 工期 ↔ 团队，任何一处改，回数字底座改再同步；交稿前逐项核对加总，别留旧版残数（分项之和必须等于总价）。
- **可选项与核心交付分开计。** 明确「核心交付总价」和「含可选项总价」，让评审看得清哪些是必选、哪些可裁剪。
- **付款进度、维护费、币种 / 税 / 有效期 / 汇率**等条款齐全；维护费基数和比例写清（如总价的某百分比 / 年）。
- **假设项标注。** 依赖待定信息的估算（费率、基础设施、额外单价）标成假设 / 待校正，不要伪装成已敲定。

## 6. 配图（适用于所有章节）

文字讲清后，在关键处补图能大幅提升可读性与说服力。**按内容性质选工具，别过度配图——一个章节通常 0–1 张图，只在文字说不清的复杂链路才配。**

| 内容性质 | 用什么 | 为什么 |
|---|---|---|
| 流程 / 状态机 / 决策分支 / 时序 / 循环，且评审可能要改框连线 | **可编辑流程图** → `feishu-editable-diagrams` skill（或 Mermaid 白板） | 这是「逻辑图」，做成可编辑而非死图 |
| 总览概念图 / 界面效果示意 / 精致架构拓扑关系图 | **精致位图** → `gpt-image-2` skill | 这是「观感图」，要好看有冲击力 |

通用要点：
- 流程图先按目标平台语法写，渲染 / 校验通过（文字溢出、遮挡为阻断项必须修）再插入。
- **配图里的文字语言全文统一**（按项目规范，常用英文），图标 / 占位若无法生成就留空、后期由人填。
- 复杂链路给「端到端」文字旁白（A→B→C→…）再配图，让读者先有画面。

### 工具链实操（飞书 + lark-cli 工作流）

> 以下是默认工具链的具体操作。若交付平台不是飞书，把「飞书写入 / lark-cli」整段换成目标平台的等价做法即可，选图原则与校验纪律不变。

- **可编辑流程图**：用 `feishu-editable-diagrams` skill 写 Feishu-friendly 的 `diagram.svg` → 用 `npx @larksuite/whiteboard-cli` 三步校验（`render` 返回 code=0、`--check` 的 errors / textOverflow / textOcclusion = 0；nodeOverlap 警告可接受）→ 用 `<whiteboard type="svg">…</whiteboard>` 经 `lark-cli docs +update` 插入 → 导出服务端预览核对。**图标一律留空、位置纯留白**（小占位框会让渲染器误判文字溢出）。
- **精致位图**：用 `gpt-image-2` skill，`bash scripts/gen.sh --prompt "<英文描述>" --out <绝对路径.png>`（走用户自己的 ChatGPT 订阅，无额外计费）。
- **插图进飞书 docx**：`lark-cli docs +media-insert --doc '<docx URL，不是 /wiki/>' --file ./x.png --as user`。注意：媒体插入需要 docx 的 document_id（不能用 /wiki/ 链接）；只能插在文末，再用 `block_move_after` 挪位；`--file` 用相对路径（先 cd 到文件目录）。
- **纯流程 / 数据类**也可直接用 Mermaid：飞书 docx XML 里写 `<whiteboard type="mermaid">…</whiteboard>`，箭头写 `--&gt;`、`&` 写 `&amp;`、标签避免 `<br/>`；飞书支持 gantt、**不支持 quadrantChart**（风险矩阵这类改用表格）。
- **飞书写入前提**：lark-cli 需在真机配好并通过 user 身份认证；沙盒里没有，须经 `osascript` 在真机 shell 跑，每条命令前 `export PATH=$HOME/.npm-global/bin:$PATH`。长任务（生图、whiteboard-cli 冷启动）用 `nohup … &` 后台跑再轮询，避免超时。

## 收尾自检清单（交稿前过一遍）

- [ ] 全文腔调是「主动方案」，没有大段「我们将满足……」的招标回声
- [ ] 每条招标要求都被响应；矩阵分级 + 编号 + 回标位置齐全，总条数核对无误
- [ ] 术语 / 技术口径 / 可选边界全文一致
- [ ] 报价 ↔ 工期 ↔ 团队三处数字对得上；分项之和 = 总价
- [ ] 竞品名 / 未授权客户名 / 旧口径关键词全文搜一遍，正文已清零
- [ ] 待确认项集中列在文末，正文干净无批注
- [ ] 配图按性质选了对的工具，没有过度配图
- [ ] 版本命名带 vN，旧版归档，索引 / 交接简报已更新
