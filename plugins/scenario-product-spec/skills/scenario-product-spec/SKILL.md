# 场景化产品方案写作（Scenario-Embedded Product Spec）

## 这个 skill 解决什么问题

很多产品方案/功能方案是"需求清单的翻版"——每条功能只有一句平白的陈述（"场次开始前不可记出席"），评审读完知道"有这功能"，却感受不到"产品怎么用、业务怎么转、你是否真懂这门生意"。本 skill 教你把每条功能**嵌进场景**，让方案读起来像在讲"系统在真实业务里如何运转"，从而：①体现对业务的深度理解（投标技术分/产品理解分的主要来源）；②让非技术评审也能看懂；③把碎片化的需求织成有逻辑的模块故事。

核心动作只有一个：**把"功能短句"改写成"场景化业务语句"**，再按模块组织成端到端叙事。

## 一、黄金改写公式（最重要）

每条功能都按这个结构展开成一句或几句完整的话：

> **谁（角色）** 在 **什么前置设置/场景** 下，当 **满足什么条件** 时，**系统如何响应**（必要时补一句**为何这样设计 / 业务价值**）。

不是每条都要凑满四要素，但要明显比"功能短句"更像"业务剧本"。对照感受：

**反例（干巴巴的功能短句）：**
> 场次开始前不可记出席。

**正例（场景化业务语句）：**
> 管理员可为每个场次设定开始时间；在该场次的安排日期与时间到来之前，系统一律阻止记录出席，避免提前误签。

**再来一组：**

- 反例：`退款限制至原信用卡。`
- 正例：`若原付款是信用卡，系统必须原路退回当初那张信用卡，不允许改退到别处——把财务风险锁死在原始交易上。`

- 反例：`预留超时自动释放名额。`
- 正例：`预留一经确认即扣除名额，但若在管理员可配置的时限内仍未转为正式报名，系统会自动把这些被保留的名额释放回去，避免名额被长期空占。`

写完一段后自检：**把"系统/用户/管理员/当...时"这些词去掉后还成立吗？** 如果一句话里没有动作主体、没有触发条件、只剩一个名词短语，那它还是"需求清单"，需要再展开。

详细的句式库、常见改写陷阱、中英文语气把控见 `references/writing-pattern.md`，写之前先读它。

## 二、文档骨架

按"先总览定主线 → 再逐模块讲透 → 附编号速查"组织：

1. **开篇说明**：本文与需求矩阵/功能清单的分工（**本文讲业务叙事，矩阵讲逐条合规判定，二者互补不重复**）；口径一致性声明（技术选型、术语、字段级细节"以原型/后续确认为准"）。
2. **产品理解总览**：先画出业务主线（端到端那条"骨架"，如 计划→子活动→报名→出席→分析），再讲清角色与权限模型（谁能看到什么、谁能批什么）——后面每个模块都建立在这条主线和权限模型之上。
3. **逐模块叙事**：每个模块讲"产品逻辑 + 关键业务规则（场景化）+ 复杂链路的端到端说明"。条数最多/最复杂的模块（如报名、支付、退款）重点展开，其余模块讲清逻辑即可，详略有别。
4. **端到端链路提示**：对最复杂的几条链路，单独给一段"端到端链路"文字（A→B→C→…）并配流程图（见第四节）。
5. **附录：模块 ↔ 需求编号速查表**，指回合规矩阵。

## 三、三条护栏（避免写过头/写错）

1. **不要复制需求矩阵**：本文讲"业务逻辑与场景"，矩阵讲"逐条合规判定（满足/部分/替代）"。同一条需求，两边视角不同、不重复抄。每段末尾用括号回标编号即可——**编号沿用招标/需求文档里的原始编码体系**（不同项目编码不同，如 `REQ-xxx`、`FR-xxx`、`需求 3.2.1` 等），本 skill 不规定具体编码格式，按目标项目实际用。
2. **字段级承诺写成"依原型/后续确认为准"**：细到具体字段、具体界面的部分，往往依赖最终原型或客户后续提供的规格。在需求冻结前别把范围写死，免得中标后做亏。用"以最终原型/客户后续提供的规格确认为准"这类措辞兜底。
3. **与已锁定口径严格一致**：架构、技术选型、术语、可选模块边界、命名，必须和方案其他部分（技术方案、财务方案）完全对齐。本 skill 只管"怎么讲"，不改"讲什么"的既定事实。

## 四、给文档配图（流程图 + 效果图）

文字讲清后，在关键处补图能大幅提升可读性与说服力。**分两类图，用两个不同工具**：

### 4.1 流程图 / 状态机 / 时序图 → 用 `feishu-editable-diagrams`

适用：生命周期**状态机**（如计划 Draft→Approved→Closed）、**决策分支**（如退款按付款方式分流）、**时序图**（如在线报名+支付的跨系统调用）、**循环**（如候补转正顺延）。这类图是"逻辑/流程"，且评审常想在飞书里改框连线，所以做成**可编辑白板**而非死图。

做法（详见 `references/diagrams-and-visuals.md`）：先写 Feishu-friendly 的 `diagram.svg` → 用 whiteboard-cli `render/--check/--to openapi` 三步校验（text-overflow、textOcclusion 为阻断项必须修）→ 用 `<whiteboard type="svg">…</whiteboard>` 经 `lark-cli docs +update` 插入 → 导出服务端预览核对。**图标一律留空**（小占位框），后期由人填。

### 4.2 效果图 / 概念图 / UI 示意 → 用 `gpt-image-2`

适用：开篇的**总览概念图**、模块的**界面效果示意**、精致的**架构/拓扑/关系类配图**。这类是"观感"图，用 GPT Image 2 生成精致位图。

做法（详见 `references/diagrams-and-visuals.md`）：`bash scripts/gen.sh --prompt "<描述>" --out <绝对路径.png>`（走用户 ChatGPT 订阅）。**配图里的文字一般用英文**（贴合本类投标方案的既定规范，除非用户另有要求）。生成后插入飞书 docx：`lark-cli docs +media-insert`（注意：媒体插入需要 docx document_id，不能用 /wiki/ 链接；只能插在文末再 `block_move_after` 挪位）。

### 4.3 选图原则

| 内容性质 | 用哪个 | 为什么 |
|---|---|---|
| 流程/分支/状态/时序，需可编辑 | feishu-editable-diagrams | 逻辑图，评审要能改框连线 |
| 总览/UI 效果/精致概念图 | gpt-image-2 | 观感图，要好看、有冲击力 |

**别过度配图**：一个模块通常 0–1 张图就够；只在"复杂到文字说不清"的链路才配图。

## 五、工作流程

1. **先搞清两件事**：目标文档放哪（飞书 wiki / docx / 本地 md）、有没有配套的需求清单或矩阵可回标编号。若是扩写已有文档，先读它，按公式逐条改写；若从零写，先列模块和需求编号再逐模块铺。
2. **先把文字写透**（第一、二、三节），这是主体。先本地成形为 md，便于低成本迭代。
3. **再补图**（第四节），只在关键链路补，流程图走 feishu-editable-diagrams、效果图走 gpt-image-2。
4. **收尾**：附录编号速查；与方案其他部分核对口径一致；版本命名带 vN，旧版归档。
