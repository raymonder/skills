# 场景化句式库与改写指南

> 写之前读这份。目标：把"功能短句"稳定地改写成"场景化业务语句"，颗粒度统一、语气一致。

## 一、改写公式拆解

完整结构（按需取用，不必凑满）：

```
[角色] + [前置设置 / 触发场景] + [当…条件] + [系统如何响应] + (为何 / 业务价值)
```

- **角色**：会员 / 职员 / 单位负责人(UIC) / 管理员 / 审批人 / 系统 / 外部系统名。先点明"谁"，避免无主语。
- **前置设置 / 触发场景**：谁在什么时候配置了什么、或在什么操作场景下。这是"短句"最常缺的部分——补上它，功能立刻有了上下文。
- **条件**：当满足/不满足什么时。把隐含的业务规则显性化。
- **系统响应**：系统具体做什么（放行/拦截/计算/通知/同步/释放…）。动词要具体。
- **为何 / 价值**（可选）：一句话点出设计意图或业务收益，体现"懂行"。慎用、别每句都加，否则啰嗦。

## 二、句式模板（可直接套）

- 「**当** 〔角色〕〔做某操作〕**时**，系统会 〔响应〕，〔从而/避免 …〕。」
- 「〔角色〕可 〔配置/设置〕〔某项〕；〔在某条件下〕，系统 〔响应〕。」
- 「若 〔条件 A〕，系统 〔响应 A〕；若 〔条件 B〕，则 〔响应 B〕。」（用于分支/分流规则）
- 「为了 〔业务目的〕，系统 〔机制〕——例如 〔具体例子〕。」（用于讲机制 + 举例）
- 「〔角色〕一经 〔动作〕，系统即 〔即时响应〕；但若 〔超时/异常条件〕，系统会 〔补偿响应〕。」（用于带时限/状态流转）

## 三、改写前后对照（多组）

| 反例（功能短句） | 正例（场景化业务语句） |
|---|---|
| 仅 Active 用户可登录。 | 系统对接协会 SSO 完成身份识别；只有在 SSO 中状态为 Active 的用户才被放行登录，已离职或停用的账号即便记得网址也无法进入。 |
| 支持批量导入计划。 | 在高峰季前需集中铺设大量计划时，同事可用 CSV/Excel 一次性批量创建计划与子活动；引擎在写入任何记录前先跑自动校验，把不合规数据挡在门外。 |
| 一笔付款可对应多笔报名。 | 因为现实中一笔付款可能对应多笔报名（典型如家长一次性为全家几个孩子缴费），系统把报名记录与付款记录双向关联，从任一方都能快速跳到另一方。 |
| 审批分 6 级。 | 审批按 6 级层级运作：一个请求从 Level 1 按顺序逐级上行、最高至 Level 6，并自动路由到同一负责单位内下一层级的指定审批人——保证"谁的单位谁负责、逐级问责"。 |
| 提供受限模式。 | 当系统进入受限模式时，被标为"受限编辑者"的用户操作照常，而"受限读取者"则功能受限（如子活动编辑被阻止、柜台报名不可用）——相当于高峰季或维护窗口的降级开关。 |

## 四、常见陷阱

1. **只换了标点没加信息**：把句号改成逗号、堆两个短句，但仍没有角色和场景——无效。必须补进"谁/在什么场景/什么条件"。
2. **过度堆"为何"**：每句都加一句价值论证会很啰嗦。只在该规则确有非显然的设计意图时点一句。
3. **编故事编过头**：场景要真实、贴合该需求原意，不能虚构原文没有的功能或承诺。**场景化是"讲清"已有需求，不是"扩张"需求**。
4. **丢了编号**：改写后忘了回标需求编号。每条/每段末尾用括号标上**招标/需求文档里的原始编号**（不同项目编码体系不同，按实际用，如 `REQ-3.2.1`、`FR-018`），方便评审交叉核对。
5. **字段写太死**：把"约 80 个字段，含文本/数值/日期/下拉"写成精确字段清单——这类细节应留"以原型最终确认为准"。
6. **颗粒度忽大忽小**：同一份文档里，有的模块一句话、有的模块写满半页。按"复杂度"分配详略：核心复杂模块展开，简单模块讲清即可，但每条都要达到"场景化"基线。

## 五、中英文语气把控

- 正文中文用**现在时、主动语态、口语化但专业**："当…时，系统会…"。避免翻译腔（"该功能被提供以…"）。
- 首次出现的英文术语保留原词并括注中文（如 Programme Plan 活动计划、UIC 单位负责人），其后统一用中文。
- 若方案有"配图文字用英文"之类既定规范，正文中文、图内英文，分开遵守。
- 保持与全篇一致的人称：通常用"系统/同事/职员/会员/管理员"，不要一会儿"用户"一会儿"客户"。

## 六、收尾自检清单

逐条过一遍：

- [ ] 每条功能都有"角色 + 场景/条件 + 系统响应"，不再是裸名词短语。
- [ ] 复杂分支/分流写成了"若 A 则…；若 B 则…"的清晰规则，而非一句含糊带过。
- [ ] 每段回标了需求编号。
- [ ] 没有复制需求矩阵的逐条判定（视角互补）。
- [ ] 字段级、界面级细节都加了"以原型/后续确认为准"的兜底。
- [ ] 术语、技术口径与方案其他部分一致。
- [ ] 详略按复杂度分配，核心模块（如报名/支付/退款）明显更厚。
